핵심 원칙 — 콜로케이션
1. app/은 얇게, features/는 두껍게 — page.tsx는 features의 컴포넌트·쿼리를 조립만. URL 구조 바꿔도 로직은 그대로.

2. 함께 바뀌는 건 함께 둔다 — 한 기능의 컴포넌트·액션·쿼리·스키마·타입이 한 폴더에. "모집 고칠 일 있으면 features/recruit만 본다."

3. 읽기/쓰기 분리 — queries.ts(조회, 서버 컴포넌트용) + actions.ts(변경, Server Action). 서버 우선 아키텍처와 정확히 일치.

4. 라우트 전용 컴포넌트 — 한 페이지에서만 쓰는 건 app/.../_components/ (밑줄=라우팅 제외). features 안 감.

5. 배럴 파일 주의 — 폴더마다 index.ts 몰아서 re-export는 트리쉐이킹 방해·순환참조 유발. 명확한 경계에서만.
읽기 / 쓰기 흐름
흐름경로
읽기 (조회)서버 컴포넌트 → features/recruit/queries.ts → Prisma → DB
쓰기 (변경)form action → features/recruit/actions.ts ('use server') → Prisma → revalidate
API (RN 대비)app/api/recruit/route.ts → 같은 queries.ts 재사용
Phase 2 이점 — 백엔드를 Spring으로 뺄 때, 각 feature의 queries.ts + actions.ts가 그대로 Spring 서비스 계층에 대응. 기능별로 로직이 모여있어 이관이 명확.
